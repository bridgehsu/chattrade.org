# 异常处理与一致性保障

<div class="doc-lead">用订单、成交和账务事实共同判断结果。</div>

## 典型场景 {#scenarios}

| 场景 | 设计上应如何处理 |
| --- | --- |
| 提交后超时 | 使用原业务标识查询，先确认是否受理 |
| 余额不足 | 拒绝占用，避免订单进入可成交状态 |
| 撤单时继续成交 | 按权威处理顺序确认剩余量，再解冻 |
| 成交消息重复 | 按成交唯一标识识别已处理结果 |
| 结算只完成部分动作 | 保留处理中状态与恢复任务，核对每条账务事实 |
| 撮合重启 | 恢复未完成委托及处理边界，避免重放已结算资金 |

处理时建议明确权威顺序：撮合产出的成交与订单剩余量，优先于页面余额展示；账务流水用于解释可用/冻结为何如此，而不是由前端快照倒推订单状态。幂等键至少覆盖「同一业务编号的下单」与「同一成交标识的结算」。

## 用贯穿示例核对 {#example}

沿「买入 0.01 BTC，成交 0.006，撤销 0.004」做一次结果核对：

1. 委托最终状态应为已撤销（或产品定义的等价终止态），已成交量 0.006，剩余 0。
2. 成交记录存在一笔 0.006 BTC @ 60,000，金额 360 USDT。
3. 买方可用 + 冻结 + 已支出 USDT 应回到可解释的 1,000 口径（忽略费用时：640 + 0 + 360）。
4. 买方 BTC 增加 0.006；若有手续费，净增加量与费用流水一致。
5. 卖方对称减少 0.006 BTC 占用，并增加对应 USDT（扣费前）。

任何一项对不上，都不要只改余额；应先定位是委托状态、成交缺失，还是占用/解冻/入账缺一步。

## 检查方法 {#check}

沿业务编号核对委托、成交、占用、扣款与入账。只看页面余额或最后一条报错无法判断完整结果。异常修复应留下原因、审核和处理记录。

建议的最小检查清单：

| 检查项 | 通过标准 |
| --- | --- |
| 业务编号 | 能唯一定位到一笔委托 |
| 委托状态与数量 | 原始 = 已成交 + 剩余（终止后剩余为 0） |
| 成交唯一标识 | 无重复结算 |
| 资金占用 | 冻结变化与剩余量、价格规则一致 |
| 入账流水 | 买卖双方资产变化可对齐同一成交 |

这些是应满足的设计目标。工程中可见撮合恢复、事件处理和资金相关实现，但是否覆盖所有异常需要运行测试与部署核查。对账与资金一致性的一般方法，见[对账与资金一致性](/ledger/reconciliation)。
