# 系统架构

<div class="doc-lead">现货链由委托、撮合、账户和行情共同完成。</div>

## 模块划分与职责 {#modules}

| 模块 | 主要职责 | 阅读时抓住什么 |
| --- | --- | --- |
| coinex-entrust | 委托相关业务与查询 | 订单受理、规则校验、委托查询入口 |
| coinex-match | 订单簿、撮合事件及相关账户运行态处理 | 谁持有未成交意图、何时产生成交 |
| coinex-account | 业务账户与账务相关服务 | 可用/冻结口径与资金变动记录 |
| coinex-market | 行情相关处理 | 深度、最新价、K 线等展示数据 |
| 用户与商户服务 | 身份、交易产品和商户上下文 | 谁能交易、交易哪个产品 |

现货链路不等于「一个服务包办一切」。委托服务负责把交易意图变成可追踪订单；撮合服务维护订单簿并产出成交；账户侧保证资产变化可解释；行情侧把结果变成用户可见的盘口与曲线。功能全景中现货一行也对应委托与撮合，行情能力由 `coinex-market` 补充，详见[功能全景](/pages/0102)。

## 模块交互与数据流向 {#dataflow}

<Flow :steps='["用户提交交易意图","委托与规则检查","账户资金占用","撮合处理","订单 / 资产 / 行情更新"]' />

图示描述业务逻辑先后关系，不保证每一步是独立远程调用或同一数据库事务。已检查的撮合服务本身也包含账户缓存和资产变动相关处理，因此不能机械理解为：冻结一定只发生在账户服务、结算一定只发生在另一个服务。

阅读数据流时建议追问四个问题：

1. 谁接受订单并给出可查询的业务编号？
2. 谁决定这笔单能否进入订单簿？
3. 谁在成交后改写订单剩余量与资产？
4. 谁把深度、最新成交推给客户端？

未完成委托的查询、初始化撮合事件与本地恢复边界，属于存储与恢复设计，详见[数据存储与缓存](/pages/0303)。本页只说明现货链路职责，不把恢复实现写成已完成生产审计。

## 工程事实 {#facts}

以下内容来自工程检查，属于可观察事实，不是流程图上的推断：

- 现货撮合可见红黑树订单簿、买卖价格队列、Disruptor 事件处理与初始化撮合事件。
- 委托类型枚举包含限价与市价。
- 委托状态包含未成交、部分成交、完全成交与已撤销。
- 撮合服务中存在账户缓存与资产变动相关处理，画模块图时不要假设「撮合只比价、账户只记账」的绝对切分。

存储枚举值、内部队列名与服务间具体协议路径不在本手册展开；需要对接实现时，应回到工程与接口约定章节核对。
